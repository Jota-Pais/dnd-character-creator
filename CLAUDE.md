# D&D Character Creator — CLAUDE.md

## Visão do Produto

Qualquer pessoa que decida jogar D&D — mesmo pela primeira vez — deve conseguir criar uma ficha em **poucos minutos**, sem assistir a vídeos nem ler centenas de páginas de regras, mantendo **controle total das próprias escolhas** e vivendo uma experiência **gamificada e prazerosa**.

Toda decisão de produto e design serve a esse objetivo: guiar o iniciante sem tirar dele o controle, esconder a complexidade das regras (mas nunca as escolhas) e tornar a criação um momento divertido — não uma lição de casa.

## Arquitetura

- **SPA front-end pura**, sem backend
- Persistência local no navegador (localStorage na V1, possivelmente IndexedDB no futuro)
- **Sistemas Multi-RPG (Arquitetura Modular):** O núcleo da aplicação (`core/`) é completamente agnóstico de regras de negócio. Todos os dados, regras e telas específicas ficam isolados nos seus respectivos módulos de sistema (ex: `systems/dnd5e`) — as regras no motor (`packages/rules`), as telas no site (`apps/web`); ver "Estrutura do repositório" abaixo.
- Deploy estático na Vercel (`vercel.json` na raiz), com CI de lint, testes e build via GitHub Actions (`.github/workflows/ci.yml`) a cada push/PR na `main`
- Sem servidor por enquanto: não sugerir API routes, server actions ou qualquer arquitetura com servidor próprio. O servidor (conta e sincronização) é plano do dono para depois (decisão de 2026-10-29), e o motor de regras já fica pronto para ele
- **Aleatoriedade com fonte única** (Fase 0 do modo de jogo, 2026-10-29): todo sorteio passa pelo motor de dados do núcleo (`packages/rules/src/core/dice`: `roll`, `cryptoRoller`/`cryptoRng`), com o roller injetável para os testes fixarem as faces (`sequenceRoller`) — os dados do criador também (4d6 em `rollAbilityScore`, PV por rolagem, ouro inicial). Todo id sai de `createId` (`packages/rules/src/core/utils/id.ts`: `crypto.randomUUID`, e fora de contexto seguro, em http pelo IP da rede, o prefixo, o momento e o `cryptoRng`). Só o `cryptoRng` chama o `Math.random`, como último recurso, e `core/utils/__tests__/id.test.ts` cobra isso lendo o código do pacote e do site.

### Estrutura do repositório (workspaces npm, 2026-10-29)

O projeto em partes, por decisão do dono: motor de regras, site e app de celular (iPhone: o site instalável pela tela inicial; Android: APK que abre o site publicado). O servidor (conta, sincronização) vem depois e usa o mesmo motor.

- **`packages/rules` (`@rpg/rules`) — o motor, puro.** O que não depende de tela: `core/dice`, `core/utils/{id,canonicalJson}`, `systems/<sistema>/{data,types,utils}` dos dois sistemas (com os testes) e `test/fixtures.ts`. Roda no navegador e no Node: o tsconfig do código do pacote não tem a lib DOM nem os tipos do Vite (`import.meta.env`, import de `.css` ou de imagem não compilam; o que ele usa de comum aos dois, `structuredClone` e `crypto`, está declarado em `src/runtime.d.ts`), os testes rodam em ambiente node, sem jsdom (o `tsconfig.test.json` do pacote, com `vite/client` e `node`, é só deles), e o ESLint recusa no pacote `.tsx` e import, também por `import()`, de `react`, `react-dom`, `zustand`, `@capacitor/*` ou do site (`src/__tests__/boundary.test.ts` passa um arquivo de mentira pelas duas guardas). Sem passo de build: os `exports` apontam para o TS-fonte. Por isso, **no Node o motor entra por um bundler ou carregador de TS** (o Vite e o Vitest de hoje; no servidor, o que ele usar, como o `tsx` ou o esbuild): o Node puro não o carrega (os imports relativos não têm extensão, e os JSON entram sem `with { type: 'json' }`; conferido em 2026-10-30 com o Node 24, `ERR_MODULE_NOT_FOUND`).
- **`apps/web` (`@rpg/web`) — o site.** Componentes, stores, App, main, GlobalGallery, index.html, public, vite.config, CSS e o setup de teste (jsdom). Importa o motor pelo nome, com o caminho de dentro de `packages/rules/src`: `@rpg/rules/systems/dnd5e/utils/rollGuide`, `@rpg/rules/systems/dnd5e/data/tools.json`, `@rpg/rules/core/dice`; nos testes do site, `@rpg/rules/test/fixtures` (e o `vi.mock` de módulo do motor usa o mesmo nome).
- **Onde mora cada caminho curto deste arquivo.** `utils/…`, `data/…` e `types/…` de um sistema estão em `packages/rules/src/systems/<sistema>/`; `components/…` e `stores/…`, em `apps/web/src/systems/<sistema>/`. Ficam no site, apesar da pasta: `utils/storage.ts` dos dois sistemas e `utils/playStorage.ts` (localStorage, arquivo, download), `core/types/system.ts` (tipos do React), `core/utils/galleryGrouping.ts` (que o lê) e `core/{stores,systems}`.
- **Regra do pacote puro.** Arquivo novo vai ao motor quando é regra e não precisa de tela; o que importa React ou zustand, toca API do navegador (window, document, localStorage, matchMedia, clipboard) ou é ajudante de tela (os `.ts` de `components/play`, como `hpVitals.ts`) fica no site. O site importa o motor, nunca o contrário. Classe do Tailwind nunca mora no pacote: o Tailwind só procura classes dentro de `apps/web`, e o teste de cores do tema só lê o site — por isso as cores dos elementos do Ordem moram em `apps/web/src/systems/ordem/components/common/elementColors.ts`, não no `ritualUtils`.
- **`apps/mobile` (`@rpg/mobile`) — o APK do Android.** O Capacitor 8 e o projeto nativo (`android/`), que abre o site publicado; nenhum código do site mora aqui. Ver "App do Android (APK)" abaixo.
- **Comandos, sempre da raiz.** `npm run dev` (o Vite do site; outra porta com `npm run dev -- --port N --strictPort`), `npm run build` (`tsc -b` com as referências + `vite build`, saída em `apps/web/dist`), `npm test` (Vitest com os projetos `rules`, `web` e `mobile`; um só com `--project rules`), `npm run lint` e `npm run typecheck`. O APK: `npm run apk:release -w @rpg/mobile` (ou `apk:debug`). Portões antes do commit, pelo binário: `node ./node_modules/vitest/vitest.mjs run`, `node ./node_modules/eslint/bin/eslint.js .`, `node ./node_modules/typescript/bin/tsc -b` e `npm run build`. Dependência nova vai ao `package.json` do workspace que a usa (`npm install <pacote> -w @rpg/web`); ferramenta do repositório (ESLint, TypeScript, Vitest), à raiz.
- **Publicação.** A Vercel publica da raiz pelo `vercel.json` (framework Vite, `npm ci`, `npm run build`, saída `apps/web/dist`), que vale sobre as configurações do painel. A origem `https://dnd-character-creator-gamma.vercel.app` não pode mudar: as fichas no localStorage são dela, e o APK abre esse endereço. Os `scripts/` gravam nos dados do motor (`packages/rules/src/systems/<sistema>/data`); `docs/` fica na raiz.

### App instalável e sem rede (2026-10-29)

O site é o app do celular (iPhone: instalado pela tela de início; Android: o APK abre o site publicado) e abre sem rede depois da primeira visita. Como funciona, como atualiza, os limites do iPhone, a medida do carregamento e o roteiro no aparelho: `docs/app-instalavel.md`.

- **Service worker do vite-plugin-pwa** (`apps/web/vite.config.ts`), com o registro nosso em `apps/web/src/core/pwa/serviceWorker.ts` (só no build de produção, depois do `load`). Guarda o build inteiro e **só o que é do site**: nenhuma fonte, script ou imagem de outro domínio (as fontes vêm do `@fontsource-variable`), nenhum `runtimeCaching`. Arquivo novo que precise abrir sem rede casa com o `globPatterns` do Workbox (html, js, css, woff2, webp, png, svg, webmanifest); extensão nova entra lá.
- **Versão nova só na próxima abertura.** O SW novo baixa e espera; nada recarrega a página sozinho, nunca no meio do jogo. O único recarregar é o "Atualizar agora" do aviso da galeria (`GalleryNotices.tsx`), pelo toque. Nada de `skipWaiting`/`clientsClaim` automáticos nem `registerType: 'autoUpdate'`. No APK, a "próxima abertura" só existe quando o Android encerra o app (ou ele sai dos recentes): o voltar da galeria minimiza, e o ícone traz de volta a mesma página, com a versão velha. Por isso, lá, o aviso diz "Atualização pronta: toque em Atualizar agora para usá-la." (e "versão nova do app" fica só para o APK novo); aplicar sozinho na volta à galeria é decisão pendente do dono.
- **O que fica fixo nas bordas soma a área segura** (`viewport-fit=cover`): `env(safe-area-inset-*)` no que encosta no topo, no pé ou nas laterais (vitais, aviso do pé, folhas, rodapé do criador). Pseudo-elemento com `content` no CSS de base leva fonte genérica: a linha que ele abre pede a fonte, e a do site desceria junto com o JS, antes de haver texto (`indexCss.test.ts`).
- **Dados do aparelho.** O pedido de armazenamento persistente sai da camada de storage, na gravação de ficha (`requestPersistentStorage`, `core/pwa/persistentStorage.ts`): camada nova que grave ficha também chama. O que o app guarda do aparelho fora das fichas (a resposta do pedido, os avisos da galeria) vai pelo `core/utils/deviceStorage.ts` (chave `app-device`), e a galeria lê pelo `core/stores/deviceStore.ts`. Todo arquivo que o app entrega passa por `saveJsonFile` (`core/utils/download.ts`): no navegador, o download de `downloadJsonFile`, que solta o arquivo um minuto depois do clique (o Safari do iPhone o lê depois) e conta como salvo na hora; no APK, o "Salvar como" da casca (ver "App do Android"), e o `onSaved` (a data da cópia de segurança) só roda com o arquivo gravado.
- **iPhone.** O app da tela de início guarda à parte do Safari e começa sem as fichas do navegador; a dica de instalar da galeria diz isso e oferece a cópia. O mínimo é o iOS 16.4 (o Tailwind 4 e o alvo `baseline-widely-available` do Vite 8).
- **O JS fica num arquivo só** (medido em 2026-10-30: a galeria aparece em 1,3 s na primeira abertura em 4G rápido, e as seguintes saem do SW). O build avisa acima de 2 MB (`chunkSizeWarningLimit`): aí, medir de novo e, passando de ~3 s, dividir (o Ordem e a impressão por `import()`).

### App do Android (APK) (2026-10-30)

O APK (`apps/mobile`, Capacitor 8) é uma casca que abre o site publicado, sem cópia do build: cada push na `main` chega ao celular na próxima abertura, e sem rede o SW do site abre a cópia guardada. APK novo só quando muda a parte nativa. Como gerar, assinar, subir a versão, testar com o site local, distribuir e os limites: `docs/app-android.md`.

- **A origem é fixa** (`PRODUCTION_URL` no `apps/mobile/capacitor.config.ts`, presa pelo teste do `apps/mobile`): as fichas do APK moram nela. Só ela navega no app, por https.
- **Código do site que só vale no APK** mora em `apps/web/src/core/native` e passa por `isNativeApp()` (o Capacitor): no navegador e no iPhone não roda, nem chama plugin. A tela acesa não tem ramo nativo: a Screen Wake Lock funciona no WebView (conferido no `KEEP_SCREEN_ON` da janela).
- **O voltar do Android** é do app (`core/navigation/back.ts`): o site não usa o histórico do navegador. Folha, menu, confirmação ou painel aberto que feche com o Esc, um ✕ ou o próprio botão (o descanso e a engrenagem do jogo) registra o voltar com `useBackHandler(fechar, 'overlay')`; tela nova com "← Voltar" registra o dela (`'screen'`); sem nada registrado (a galeria), o APK minimiza. O criador refaz o caminho desta visita (`useStepPath`, 2026-10-30): a etapa de onde se veio e, da primeira que se abriu, a galeria — a ficha aberta na Revisão pelo "Abrir" volta direto; o Esc e o "← Voltar" do rodapé seguem indo à etapa anterior do fluxo. Teste em `__tests__/backButton.test.tsx`.
- **O que o WebView não faz, a casca faz** (`NativeShellPlugin.java`, chamado por `core/native/nativeShell.ts`; desde o versionCode 2): o download do site (link com `download` para um `blob:`) o WebView ignora, sem arquivo nem erro, e o `window.print()` ele não implementa. Por isso arquivo passa por `saveJsonFile` (o "Salvar como" do Android, `saveFile`) e o "Imprimir / Salvar PDF" por `printPage` (`core/utils/print.ts`: a impressão do Android, `print`). O APK velho responde `UNIMPLEMENTED`, e o site avisa que precisa do APK novo. Método novo da casca entra na interface `NativeShellPlugin` do site e como `@PluginMethod` no Java (o teste do `apps/mobile` cobra os dois lados), com versionCode e mínimo novos.
- **Plugin nativo novo** entra no `package.json` do `apps/mobile` (o código nativo) e do `apps/web` (a API JS), na mesma versão; o `@capacitor/core` e o `@capacitor/app` dos dois andam no mesmo major. Quando o site passar a depender dele, sobe o `versionCode` do APK e o `android.minVersionCode` de `apps/web/public/app-version.json`, e o APK velho avisa na galeria. O mínimo nunca passa do `versionCode` de agora (teste do `apps/mobile`).
- **A chave de assinatura nunca entra no repositório** (os `.gitignore` recusam `.jks`, `.keystore`, propriedades de assinatura e APK): o Gradle a acha por `FORJA_SIGNING_PROPERTIES` ou pelo `local.properties`. Perdida a chave, nenhum APK novo instala por cima, e a turma perderia as fichas ao desinstalar.
- **A página de erro** (`apps/mobile/www/index.html`) é a do APK sem rede e sem cópia, ou com o WebView abaixo do 111 (o mínimo do build do site: `MIN_WEBVIEW_VERSION`, o mesmo nos dois arquivos); o "Tentar de novo", o voltar dela e o WebView encerrado pelo Android são do `NativeShellPlugin.java`.

### Proficiências e efeitos (portado do módulo Ordem, 2026-08-29)

Dois motores, um em cada arquivo, espelhando o que o Ordem já fazia:

- **`utils/proficiencyUtils.ts` — quem tem o quê.** Fonte única de perícias, ferramentas, idiomas, armaduras, armas e resistências, agregando raça, classe (com o subconjunto de multiclasse da p. 166), subclasse e talento. Nada de agregação paralela em outro módulo.
  - A exclusão é **por slot**, não por fonte: a lista de perícias da classe e os extras da subclasse são concessões independentes, e cada classe da multiclasse tem as suas. É o que impede repetir uma perícia (regra da p. 125).
  - Exceção: o picker de *expertise* (Domínio do Conhecimento) **não** exclui — lá dobrar uma perícia que você já tem é o ponto.
  - **Proficiência repetida** (decisão do usuário, 2026-10-26): perícia ou ferramenta *escolhida* que outra fonte passou a dar (antecedente ou raça trocados depois, ficha antiga) **nunca é apagada em silêncio** — nada de `useEffect` de filtro nas etapas. `getRepeatedProficiencies` acha a repetida sobre as mesmas concessões com dono (raça, cada slot de classe da multiclasse, antecedente, cada talento): a fixa tem a palavra final; entre duas escolhidas, troca a do passo posterior do wizard (raça → talento racial → classes, a inicial antes das adicionais → talentos de ASI → antecedente). A etapa dona da escolha reprova em `isStepComplete`, com o motivo de `formatRepeatedProficiency` em pendingReasons, e o seletor mantém a escolha marcada, destravada, com o aviso (`getRepeatedProficiencyNotes` / `ClassSlotProficiencies.repeated*` → `RepeatedProficiencyNotes`). As do Domínio do Conhecimento repetem sem pendência. **Idioma** escolhido segue a mesma regra (decisão de 2026-10-28): é o terceiro tipo de concessão do motor (raça, subclasse, antecedente, talento), e o `LanguagePicker` recebe os avisos em `repeated`. A etapa da **fonte** também avisa (2026-10-28): `RepeatedProficiency.sourceOwner` diz quem causou, `getRepetitionsCausedBy` acha o que o antecedente ou a raça repetiu em escolha de outra etapa, e `RepetitionsCausedNotes` mostra com o atalho para a etapa dona (`getOwnerStep`) — a pendência continua lá. Fixa × fixa (Meio-Orc + Soldado; druida + Eremita) não vira pendência: não há escolha a trocar, mas a p. 125 deixa escolher outra do mesmo tipo, então o antecedente abre uma **substituta opcional** por repetição (`getBackgroundFixedOverlaps`, `backgroundChoices.substituteSkills`/`substituteTools`); só valem enquanto a repetição existe (`getBackgroundSubstitutes`), e entram no motor como escolha do antecedente.
  - **Ferramenta à escolha da classe** sai de `getClassToolChoices` (classUtils): as da classe inicial ou, na classe adicional, o instrumento das Proficiências de Multiclasse (`multiclassProficiencies.instruments`: o bardo dá 1, p. 164) — seletor, validação e pendência.
  - **Especialização** também mora aqui: `getExpertiseSkills` junta a de cada classe da multiclasse (só as levas que o nível NELA libera — `expertise.grants` em `classes.json`) e a do Domínio do Conhecimento. O seletor de uma classe não oferece o que outra fonte já dobra (o bônus só se multiplica uma vez, p. 175).
  - **`getSkillChecks` é o número de cada perícia** na Revisão e no PDF (modificador + bônus dobrado, inteiro ou metade, nunca somados), e `getPassiveScore` o valor passivo. Não refazer a conta no componente — foi assim que a Especialização do bardo e a Versatilidade sumiram da ficha.
  - **Meia proficiência** (Versatilidade, Atletismo Extraordinário) é efeito `halfProficiencyOnChecks` (`rounding` + `abilities` opcional) em feature de classe/subclasse. As fontes não somam: `getCheckProficiencyBonus(draft, proficiência, atributo)` fica com a maior para o atributo do teste (perícia, iniciativa), e as linhas da Revisão e do PDF saem de `describeHalfProficiencyOnChecks`.
  - **Estilo de Luta da classe** só conta pelo `fightingStyleGrant` de `classes.json` (nível NA classe + lista: guerreiro 1º/seis, paladino e patrulheiro 2º/quatro), via `getClassFightingStyleOptions` — seletor, validação e ficha. Abaixo do nível a escolha fica no draft e não mexe em número.
  - **`getSavingThrowChecks` é o número de cada resistência**, sobre `getSavingThrowProficiencies`: classe inicial (a multiclasse não dá resistência inicial, p. 166) + Resiliente + features de classe com `savingThrowProficiencies` (Mente Escorregadia, Alma de Diamante), estas de qualquer classe da multiclasse. Ler `cls.savingThrows` no componente foi o que sumiu com o Resiliente da ficha. Bônus que depende da situação (Aura de Proteção, p. 111) **nunca** entra aqui: é o efeito `conditionalSaveBonus` (valor por fórmula de recurso, condição em degraus pelo nível na classe dona — 3 m → 9 m no 18º), e `describeConditionalSaveBonuses` (sheetEffects) dá a linha que a Revisão e o PDF mostram junto das resistências.
- **`utils/sheetEffects.ts` — o que as características fazem.** Efeitos declarados nos dados (`types/effects.ts`), agregados aqui. Regra de ouro herdada do Ordem: **efeito incondicional entra no número da ficha; efeito condicional vira linha própria com a condição** (somar o +1 do Ambidestro mentiria pra quem usa escudo).
  - Escolhas que uma característica abre (Perito, Poliglota, Mestre de Armas, Adepto Marcial, Colégio do Conhecimento) viram **slot na etapa dona dela**, ao lado do catálogo — nunca um catálogo aninhado dentro do card.
  - **Manobras** (`utils/maneuverUtils.ts`): a lista é a do Mestre de Batalha (`MANEUVER_LIST_ID`); quem as conhece pelo arquétipo sai de `getClassManeuvers`, pelo talento (Adepto Marcial, `featSelections.maneuvers`) de `getFeatManeuvers`. Uma fonte não oferece o que a outra já ensina; repetida (ficha antiga, subclasse trocada) trava a etapa do **talento** (`getRepeatedFeatManeuvers`). A CD (8 + proficiência + FOR ou DES, atributos finais) sai de `getManeuverSaveDc` / `formatManeuverSaveDc`; as manobras do talento com a CD, de `getFeatManeuverBlock` (Revisão e PDF, sob o talento); a mesma linha para as do arquétipo, de `getClassManeuverSaveDc` (uma vez, no primeiro slot de manobras das Escolhas de Progressão).
  - Consequência de regra que a ficha não deve "resolver" sozinha vira **aviso**, não alteração de número: armadura sem proficiência (p. 144) avisa da desvantagem em vez de mexer nos valores.
  - Features de classe também declaram efeito (`effects` em `class-progression-features.json`, ex.: a Versatilidade do bardo 2), agregadas por `getOwnedClassFeatures` — cada classe da multiclasse no nível que tem nela.
  - **CA** sai só de `getSheetArmorClass` (Revisão e PDF; o texto aberto por `formatArmorClassBreakdown`). Formas de CA sem armadura são efeito (`unarmoredAc`: Defesa sem Armadura, Resiliência Dracônica) e não se somam — a ficha mostra a maior (p. 14); a mesma característica (mesmo `id`) de duas classes vale uma vez (p. 166). PV por nível da classe dona da feature é `hpPerClassLevel`; por nível de personagem (talento, raça) é `hpPerLevel`.
  - **Ataques por ação** saem só de `getAttacksPerAction` (o total, que `getSheetAttacks` leva a cada linha como `attacksPerAction` — o "2×" que a Revisão e o PDF leem da linha, nunca do total: arma de recarga fica em 1, p. 149, com nota; o Especialista em Besta é o efeito `ignoresLoading`, só nas bestas com proficiência, p. 169) e `describeAttacksPerAction` (as linhas da Revisão e do PDF). Ataque Extra é efeito (`attacksPerAction`, degraus por nível na classe dona: guerreiro 2/3/4 no 5º/11º/20º) e não soma entre classes — vale o maior (p. 166). Opção escolhida em slot de progressão também declara efeito (`effects` em `ProgressionOption`): a Lâmina Sedenta é `conditionalAttacksPerAction`, linha com a condição, que some com Ataque Extra. Nunca procurar feature pelo nome.
  - **Deslocamento** sai só de `getSheetSpeed` (raça + bônus ativos) e `describeSpeedBonuses` (as linhas da Revisão e do PDF); metros sempre por `formatMeters`. Talento é `speedBonus` (incondicional). Bônus que depende do equipamento é `equipmentSpeedBonus` (degraus pelo nível na classe dona + `requires`: Movimento Rápido sem armadura pesada, Movimento sem Armadura sem armadura nem escudo): a ficha sabe o que está equipado (o mesmo `getEquippedArmor` da CA), então **entra no número quando a condição é cumprida** e vira linha — somada ou não, com o motivo. A armadura vestida sem a Força da tabela (`strengthRequirement`) tira 3 m (p. 146) — por isso as duas funções recebem os **atributos finais**, como a CA —, e o traço que anula a redução é efeito racial (`heavyArmorSpeedUnreduced`, o Deslocamento do anão, p. 20): o número fica intacto e a linha diz que foi ignorada.
  - **Ferramentas**: o nome sai só de `tools.json` (`getToolName`; `TOOL_NAMES` da raça é derivado dele — o item leva o nome da tabela de equipamento, p. 156, o texto do traço segue o livro). Traço que chama a ferramenta pelo nome do livro declara `toolNote` (`{ tool, after }`, races.json): na carga de `RACES`, o nome de tools.json entra entre parênteses logo depois de `after` — "ferramentas de engenhoqueiro (Ferramentas de Funileiro)", igual na etapa Raça, na Revisão e no PDF. Item que vale como ferramenta sem ser uma declara `countsAsTool` em `general-items.json` (os Dados de Osso do Soldado → `dice-set`, p. 142): mantém o nome no inventário, e `getToolEquivalent` resolve a equivalência para a proficiência e o aviso de ferramenta sem proficiência (`getUnproficientTools`, que diz "Dados de Osso (Conjunto de Dados)").
  - **Traços raciais** listados lado a lado (etapa Raça, Revisão, PDF) não repetem nome entre raça e sub-raça (teste de dados); a key das listas é posição + nome. Raça que vale sem sub-raça declara `baseOption` (o Humano Padrão: a Variante é regra opcional, p. 31): a etapa Raça mostra a opção como card, marcada sem sub-raça, e `requiresSubrace` deixa de cobrar (validação e pendência; decisão de 2026-10-28).
  - **Compras do método riqueza** só valem com o método riqueza ativo (p. 145: equipamento inicial OU compra): toda leitura passa por `getActivePurchases` (equipmentUtils) — CA, deslocamento, Artes Marciais, avisos de proficiência, ataques, inventário e dinheiro. Trocar de método não apaga o carrinho; fora da própria loja (EquipmentStep), nunca ler `equipment.purchasedItems` direto.
  - **Linhas de ataque** saem só de `getSheetAttacks` (`utils/attackUtils.ts`: uma linha por arma carregada + o golpe desarmado, que toda ficha tem, p. 197), e a conta de cada linha é `getWeaponAttack` / `getUnarmedStrike` (`utils/weaponFormat.ts`). O que as características fazem nelas é efeito: `weaponAttacks` (Estilo de Luta em `FIGHTING_STYLES`, Golpes de Chi) com escopo de arma — `attackBonus` é incondicional e entra no número (Arquearia), `note` é condicional e vira nota na arma (Duelismo, Armas Grandes), `conditionalDamage` é bônus de dano condicional cujo valor é um recurso da mesma característica (Dano de Fúria: escopo `melee-strength`, nota em toda arma corpo a corpo com a ressalva da linha — acuidade com Destreza vale atacando com Força, arremesso só sem arremessar — e o bloqueio da armadura pesada; `getWeaponAttackEffects` calcula no nível NA classe dona, com os atributos finais; o golpe desarmado também leva a nota — não é arma, mas é ataque corpo a corpo com arma, ver "pt-BR × inglês" —, e os escopos que o alcançam saem de `isUnarmedStrikeInScope`: `unarmed`, `melee-strength`, `weapon-attack` e `melee-weapon-attack`, os que falam do ataque, nunca os de arma; na linha de dano fixo que dá 0 ou menos, a nota diz a conta inteira — "com ele, o dano é 1 (1 − 2 + 2)" —, porque o piso 0 é sobre o total); `martialArts` (dado no recurso da mesma feature, `requires` de equipamento como o deslocamento: entra no número das armas de monge e do golpe desarmado quando cumprida); `unarmedDamageDie` (Especialista em Briga). Dano fixo (golpe desarmado, zarabatana) sai resolvido ("3", não "1+2"). A nota da regra-base do ataque da outra mão (p. 197) só aparece com duas armas leves corpo a corpo carregadas (`carriesTwoLightMeleeWeapons`, contando quantidade); a do Estilo Combate com Duas Armas, sempre. Versátil é segundo valor no dano (`formatAttackDamage`). Estilo de Luta possuído (inclusive o Adicional do campeão) vem de `getOwnedFightingStyleIds`.

  - **Recursos** (usos, poços, dados que crescem: Fúria, Chi, Inspiração de Bardo, Cura pelas Mãos, Sortudo, Arma de Sopro) também são efeito: `effects.resources` na feature de classe/subclasse, no talento (`feats.json`) ou no traço racial (`races.json`), calculados por `getSheetResources` — feature de classe no nível NA classe dona; raça e talento no nível de personagem — com os atributos finais. Cada recurso leva a origem (`source`), e a ficha mostra um bloco por origem. Mesmo `id` de duas fontes não soma (vale o maior, p. 166), salvo `addsToExisting` (o dado a mais do Adepto Marcial). A conta e o texto (`describeResource` / `formatResourceLine`) moram em `utils/classResourceUtils.ts` — a Revisão e o PDF leem de lá.

Ao adicionar uma característica nova, prefira declará-la como efeito nos dados a espalhar `if` pela UI.

**Modelo de ficha** (`utils/sheetModel.ts`, Fase 0 do modo de jogo, 2026-10-29): as listas que a Revisão, o PDF e o jogo mostram são agregadas uma vez só — a conta montada dentro de um componente foi o que deixou o Iniciado em Magia de fora do jogo. `getStartingInventory` é o inventário inicial (equipamento da classe no método padrão, com o fatiamento das opções em `resolveOptionItems`; compras no método riqueza; o do antecedente nos dois), cada item com id, quantidade, rótulo e origem: o PDF lê os rótulos, a Revisão filtra pela origem e as armas dos ataques (`getCarriedItems`, attackUtils) tiram os ids. `getKnownSpells` são as magias conhecidas por via — por classe conjuradora, cada uma uma vez e com o grupo do slot de progressão de onde veio, os blocos de talento, o truque da raça e o da subclasse, as inatas liberadas no nível —, e `listKnownSpells` o grimório do PDF; a aba Regras monta os blocos daí, e a Revisão e o PDF leem dela as Magias Raciais e os blocos de talento. Lista nova que mais de uma tela mostra entra aqui.

**Texto das características de classe** mora só em `class-progression-features.json` (classes.json não tem mais cópia; etapa Classe, Revisão e ficha leem via `classUtils`). É texto de mesa, não resumo de card: alvo, alcance, ação/reação, momento, duração, término, imunidade e recarga, conferidos com o livro. Valor que escala e já é recurso calculado aponta para "Recursos", nunca número fixo.

**Conjuração** (`utils/spellUtils.ts`) vem da classe ou, quando a classe não conjura, da subclasse: o Cavaleiro Arcano e o Trapaceiro Arcano têm `spellcasting` próprio em `classes.json` (lista de mago, `schoolRestriction`, `requiredCantrips`), e as tabelas de truques e magias conhecidas ficam em `progression.json` pelo id da subclasse (espaços na tabela `third`). Nunca ler `cls.spellcasting` direto: `getSpellcastingSource` (classUtils) / `getEntrySpellcasting` resolvem quem conjura, e `getCasterEntries` é a lista que a etapa Magias, a Revisão e o PDF usam. Truque dado pela característica (mãos mágicas) é derivado, não gravado no draft. O tipo de conjurador vem do `casterProgression` de `classes.json`; o pool da multiclasse usa `getCombinedCasterLevel` (p. 166-167).

**Escolhas de progressão que dependem de outra** (`progression-choices.json`, `utils/progressionChoiceUtils.ts`, `utils/progressionOptions.ts`) — padrão da Dádiva do Pacto do bruxo (p. 58-59), que é slot de progressão, não campo novo no draft:
  - **Slot condicional:** `requiresPick` no slot faz ele existir só com aquela opção marcada num slot já liberado (os truques do Livro das Sombras só com o Pacto do Tomo). Por isso `getProgressionSlotsUpToLevel` recebe as `progressionChoices` da classe — sem elas, o slot condicional some; todo chamador passa. Trocar a opção esconde o slot sem apagar o que estava nele.
  - **Pré-requisito de opção:** `requiresPick` na opção (invocações de pacto: Lâmina Sedenta, Sorvedor de Vida, Livro de Segredos Antigos, Voz do Mestre das Correntes, Correntes de Cárceri), conferido por `getUnmetRequirement` / `getUnmetPickRequirements` contra `getActivePicks`. Sem ele, o card não se marca; escolha antiga que o perdeu fica pendente com motivo (draftValidation + pendingReasons), sai com aviso na Revisão/PDF (`formatUnmetPick`) e **não aplica efeito** (sheetEffects ignora). Pré-requisitos de nível e de truque continuam só texto.
  - **Slot de magia com teto próprio:** `maxSpellLevel` (0 = só truques) e `hint` (texto da etapa Classe). As magias de slot sem `countsAsKnownSpell` vêm por cima das conhecidas, num grupo por rótulo de slot (`getSecretSpellGroups`).
  - **Magia ensinada por opção:** `grantsSpells` (convocar familiar do Pacto da Corrente) — derivada para os `bonusSpells` da classe, nunca gravada no draft, e conta como fonte no aviso de magia repetida.
  - **Uma escolha por característica, nunca texto que sobe de degrau:** quando o livro deixa escolher de novo em outro nível ("o mesmo animal ou um diferente": Totem Espiritual 3º, Aspecto da Besta 6º, Sintonia Totêmica 14º do Guerreiro Totêmico, p. 50), cada característica é um slot próprio com a sua lista, derivada da mesma tabela (`totemOptions` em progressionOptions). Mudar o desenho de um slot mantém o id do que já existia, para a ficha antiga carregar com a escolha no lugar e só as novas pendentes.
  - **Escolha que qualifica a subclasse** (Ancestral Dracônico da Linhagem Dracônica, p. 80): slot da subclasse com `subclassDetail` (a palavra que antecede a opção no cabeçalho — `formatClassLevelLabel` mostra "Linhagem Dracônica, ancestral Vermelho" via `getSubclassDetails`), fora das Escolhas de Progressão. Característica que mostra a escolha declara `showsPick` (`{ slot, as? }`) em `class-progression-features.json`; `describeFeaturePick` dá a linha ("Escolha: …", "Tipo de dano: …") que `getSheetClassFeatures` leva à Revisão e ao PDF.

**Escolha com limite** ("escolha N entre…", decisão do usuário de 2026-10-26): o clique sai de `toggleChoice` / `isChoiceFull` (`utils/choiceToggle.ts`). Escolha de 1 é **rádio** — outra opção troca a marcada, sem desmarcar antes (o card desabilitado parecia travado); a de N para no limite. Nos slots de progressão, rádio é `isSingleChoiceSlot` (todo slot de 1: Dádiva do Pacto, Ancestral Dracônico, totens, terreno, Caçador e, desde 2026-10-28, o cumulativo de 1 — invocação do 5º, Estilo de Luta Adicional). Já valem também a magia de 1º do Iniciado em Magia, a perícia do Humano Variante, o `LanguagePicker` (idioma de 1 da raça e do antecedente) e os seletores da etapa Classe (perícia da multiclasse, ferramenta do monge e do Mestre de Batalha, perícia do Domínio da Natureza, instrumento do bardo adicional) e a substituta do antecedente. Opção travada por pré-requisito (`requiresPick`) ou por outra fonte continua travada.

**Tabela Ancestral Dracônico** mora só em `data/dragon-ancestors.json` (`utils/dragonAncestors.ts`): as sub-raças do draconato apontam para a linha (`dragonAncestor`) e ganham os traços Tipo de Dano e Área do Sopro na carga de `RACES`; o Ancestral Dracônico do feiticeiro é a lista de opções `dragon-ancestors` sobre ela. O dano por extenso também mora na tabela (`damageLabel`: "dano de fogo", mas "dano elétrico") — nunca montar "dano de ${tipo}". São escolhas separadas — a sub-raça não preenche a do feiticeiro.

**Magia repetida** entre fontes (duas classes, Segredo Mágico, truque da raça) é permitida pela regra, mas quase sempre engano: `getSpellSources` / `getRepeatedSpells` (spellUtils) acham, e a ficha **avisa sem bloquear nem apagar** — linha `formatRepeatedSpell` na etapa Magias (por seção, com ⚠ na aba e a nota "também em X" no card), na Revisão e no PDF. Não entra em `isStepComplete` nem em `pendingReasons`. Fonte nova de magia escolhida (ex.: talento que dê magia) entra em `getSpellSources`. Magia com uso próprio por descanso longo (inata de 1º+ da raça, a de 1º do Iniciado em Magia) fica de fora: esse uso não se repete na magia da classe.

**Magia de talento** (Iniciado em Magia, p. 170) é `choices.spellChoice` no talento (classes, quantos truques e magias, nível) e slot em `FeatChoiceSlots` — classe → truques → magia, gravados em `featSelections` (`spellClass`, `cantrips`, `spells`); trocar a classe limpa as magias. O que vale sai só de `getFeatSpellPicks` (classe do talento, lista dela, nível certo, até o que o talento dá) — validação, sanitização e ficha usam o mesmo filtro. Na Revisão e no PDF a seção Magias ganha um bloco por talento via `getFeatSpellBlocks` (mesmo sem classe conjuradora), com CD e ataque pelo atributo de conjuração da classe escolhida em `classes.json`, atributos finais; a magia de 1º sai com o uso (`FEAT_SPELL_USAGE`), e o recurso de uso leva o nome dela (`nameFromChosenSpell`). No jogo, o mesmo bloco vai à aba Regras (`ruleReference`) e a CD e o ataque à aba Magia pelo `getRollGuide` (`spellcasting`, chave `feat:<talento>` ao lado das `class:<classe>` — clérigo com Iniciado de clérigo tem as duas). `getOwnedFeats` mora em `utils/ownedFeats.ts` (sheetEffects reexporta) para spellUtils ler talentos sem ciclo de importação.

**Pendências** (`utils/pendingReasons.ts`): `isStepComplete` continua sendo o portão do Concluir, e `getStepPendingReasons` / `getPendingSteps` dizem em português o que falta em cada etapa (Revisão, sob cada etapa com o "Preencher →"; rodapé de cada etapa, o primeiro motivo). Cada motivo espelha uma verificação do validador: **regra de validação nova ou alterada muda o motivo junto** — o teste de cobertura (`pendingReasons.test.ts`: motivos vazios ⇔ etapa completa num leque de fichas) cobra. Nunca bloquear sem dizer por quê, nem listar o que não bloqueia.

**Magia escolhida em slot de progressão que ocupa vaga da tabela** declara `countsAsKnownSpell` no slot (`progression-choices.json`): os Segredos Mágicos do bardo "já estão incluídos" nas Magias Conhecidas (p. 54) — Segredo truque ocupa vaga de Truques Conhecidos (decisão do usuário, 2026-10-25); os Adicionais do Conhecimento (p. 55) não têm o campo e vêm por cima. O quanto a etapa pede sai de `getCantripColumn` / `getSpellColumn` (total, ocupadas pelos Segredos, a escolher), e os avisos de excesso de `getSpellChoiceOverflows` — a etapa Magias, a Revisão e o PDF leem daí; excesso não apaga escolha, mas trava a etapa Magias e vira motivo de pendência (`getSpellStepOverflows`, decisão do usuário 2026-10-25); `isSpellStepComplete` recebe as `progressionChoices`. O seletor de Segredos oferece só truque ou magia de nível que a classe conjura (`getSecretSpellOptions`) e trava truque novo quando os Truques Conhecidos já estão cheios de Segredos (`getSecretCantripRoom`). O que só se resolve trocando Segredo (magia acima do nível conjurável, truques-Segredo além da coluna — ficha antiga ou importada) é `getSecretSpellIssues`: reprova a etapa **Classe** e vira motivo em `pendingReasons`, nunca aviso de "desmarque na etapa Magias". Na Revisão e no PDF, os títulos das colunas trazem o total com os Segredos (`getCasterColumnHeadings`) e os Segredos saem em dois grupos — os que contam nas conhecidas e os Adicionais por cima (`getSecretSpellGroups`).

- **Atributo de conjuração é sempre o final** (`getFinalAbilityScores`: raça + aprimoramentos), na etapa Magias, na Revisão e no PDF — nunca `draft.abilityScores`. Magias escolhidas acima do teto (atributo baixado depois) não são apagadas: `getSpellChoiceOverflow` vira aviso nas três telas.
- **Segredos Mágicos** (bardo 10/14/18, Colégio do Conhecimento 6) são escolhas de progressão (`SPELL_OPTIONS_LIST_ID`), mas são magias da classe: saem em `bonusSpells` de `getCasterEntries` e aparecem com as magias do bardo. As **Escolhas de Progressão** da Revisão e do PDF vêm de `getProgressionChoiceBlocks` (`progressionOptions.ts`), que deixa esses slots de fora.

### Modo de jogo (ficha viva do D&D 5e, Fase 1 fechada em 2026-10-29)

A ficha usada durante a sessão: botão "Jogar" na galeria (só ficha sem etapa pendente; recarregar a página no jogo segue a mesma regra — `findResumablePlay` limpa a marca de ficha com pendência, decisão de 2026-10-28; as duas leem `canPlayDraft`, draftValidation; a galeria não conhece o D&D: o botão vem do contrato opcional `play` do `IRpgSystem` — `canPlay`, `startPlay`, decisão 10.2.12 —, e o Ordem, que não o tem até a Fase 3, não o mostra) → view `play` do `characterStore` (`playCharacter` / `exitPlay`) → `components/play/PlayScreen.tsx`, com abas Testes, Ataques, Magia, Regras, Estado e Notas. Plano, fases e o que fica para depois em `docs/estudo-dnd-beyond-modulo-jogo.md`; as regras digitalizadas e as decisões do usuário em `docs/regras-{descanso,dano-e-morte,condicoes,rolagens-e-concentracao}.md` (itens "Decidido"). As da Fase 2 (o turno completo): `docs/regras-acoes-em-combate.md` (turno, ação bônus, reação, movimento, as ações em combate), `docs/regras-conjuracao.md` (truques pelo nível do personagem, magia de ação bônus e de reação, ritual por classe) e a seção 6 de `docs/regras-equipamentos.md` (munição e carga padrão, sem a variante Sobrecarga). Campanha, mestre e multiplayer ficam fora até haver backend.

- **A ficha não muda em jogo.** O estado de jogo (`types/playState.ts`) é separado do draft e guarda só o que foi gasto ou marcado: dano tomado, PV temporários, ajuste temporário do PV máximo, espaços, Pacto e recursos gastos (por `id`, os de `getSheetResources`), Dados de Vida gastos, condições com a nota de duração, exaustão, concentração, testes contra a morte, inspiração, nota livre, histórico de rolagens e o retrato da ficha da última abertura (ver "Aviso de correção da ficha"). O que sai do livro em jogo (preparar magia, equipar) é sessão, nunca reescreve o draft.
- **Os números vêm das fontes únicas.** `buildPlaySheet(draft)` (`utils/playSheet.ts`) tira o que o jogo usa com as funções da Revisão (`getTotalHp`, `getSavingThrowChecks`, `getSheetSpeed`, `getHitDicePool`, `getCombinedSpellSlots`…) — nenhuma conta refeita. Ficha que mudou depois é reconciliada na abertura (`reconcileLoadedPlayState`), com um aviso.
- **Aviso de correção da ficha** (decisão 10.2.23, 2026-10-29). Toda abertura do jogo tira um retrato dos números (`takeSheetSnapshot`, `utils/sheetSnapshot.ts`: PV máximo, CA, CD e ataque de cada conjuração, espaços por nível e de Pacto, com as fontes da tela; o guia sobre um estado vazio, porque é a ficha e não a sessão) e o guarda no estado de jogo (`sheetSnapshot`), com o `updatedAt` da ficha na biblioteca e a impressão digital do draft (`jsonFingerprint`, `core/utils/canonicalJson.ts`). `syncSheetSnapshot` compara com o da abertura anterior: número diferente com a MESMA ficha — mesma gravação OU mesmo draft (abrir no criador e voltar regrava a data sem mudar nada; campo novo que uma atualização dá ao draft carregado muda a impressão sem o jogador mexer) — só pode ser o app, e vira o aviso `sheetCorrected` ("O app corrigiu sua ficha: PV máximo 12 → 14"); ficha mudada no criador só atualiza o retrato. Por isso a primeira abertura grava o estado. O aviso fica até o OK: mora à parte no `playStore` (`sheetCorrection`), fora da troca de avisos de cada ação (o "Desfazer" do aviso é só da ação), e o retrato novo só entra no estado no OK (`dismissNotices`) — fechado o jogo ou recarregada a página antes, ele volta; o desfazer leva o retrato atual junto, como o histórico. Limites, pendentes do dono (estudo, 10.2.23): o aviso não alcança as correções publicadas antes do primeiro retrato, e só existe no jogo (a Revisão e o PDF não avisam). Número novo que o jogador precise saber depois de uma correção entra no retrato e em `describeSheetChanges`.
- **Regras em funções puras** (`utils/playState.ts`): toda ação é `(state, sheet, …) → PlayResult { state, notices }` (`applyDamage`, `applyHealing`, `recordDeathSave`, `addCondition`, `spendHitDie`, `completeShortRest`, `completeLongRest`…). Recusa e regra em aberto viram `notice` (`refused`, `unresolvedRule`), nunca exceção nem número inventado. Os testes de regra moram em `playState.test.ts`.
- **A tela ensina a rolar; não rola** (decisão de 2026-10-25: "eles gostam de rolar seus dados por si só"). `getRollGuide(draft, state)` (`utils/rollGuide.ts`) é a receita de cada jogada da ficha — fórmula ("1d20 + 5"), notação para o motor, modo com os motivos, "de onde vem" (breakdown), notas condicionais e crítico — e `describeRollGuide` a frase pronta. O jogador digita resultado só onde o app precisa (dano, cura, d20 do teste contra a morte, Dado de Vida). Os dados do app (`packages/rules/src/core/dice`, motor puro com RNG injetável) são preferência **desligada por padrão e sem destaque** (`PlayPreferences.appDice`); rolagem do app vai para o histórico fora do desfazer (`logRoll`). O "Nova sessão" (decisão 10.2.20), no título do histórico da aba Notas, esvazia só o histórico (`clearRollHistory` / `clearRolls`, também fora do desfazer — por isso pede confirmação, no padrão dos descansos). A tela acesa (decisão 10.2.22) é preferência do aparelho ligada por padrão (`PlayPreferences.keepScreenOn`, na engrenagem ao lado dos dados do app): `useWakeLock` (`components/play/wakeLock.ts`) pede a Screen Wake Lock com o jogo aberto e visível e a pede de novo ao voltar à vista (no APK do Android também: ela funciona no WebView); sem a API, a opção dá lugar à explicação, que separa o app aberto em http pelo endereço da rede (fora de contexto seguro, `isInsecureContext`: o mesmo navegador funciona por https) do navegador que não a tem. Sem som e sem vibração.
- **Condições do Apêndice A** são dados (`data/conditions.json`, agregadas no fim de `sheetEffects.ts`: `getActiveConditionEffects`, com as derivadas — Inconsciente implica Incapacitado — e as suspensas). Mesma regra de ouro da ficha: efeito incondicional muda o número ou o modo (exaustão 4 no PV máximo, deslocamento 0 ou pela metade, na grade de 1,5 m por `halveSpeedOnGrid`), condicional vira nota na jogada.
- **O que as características fazem em jogo também é efeito declarado**, nunca `if` pelo nome: `weaponCritThreshold` (Crítico Aprimorado/Superior, escopo `weapon-attack`: as armas e o golpe desarmado), `meleeCritExtraWeaponDice` (Crítico Brutal, Ataques Selvagens, escopo `melee-weapon-attack`: as armas corpo a corpo e o golpe desarmado — nota no crítico, com o dado que a linha usa naquele ataque e a ressalva de `scopeCaveat`, a mesma do Dano de Fúria: na arma de arremesso, "sem arremessar", porque arremessar é ataque à distância; o golpe desarmado de dano fixo não tem dado a mais), `initiativeAdvantage` (Instinto Selvagem), `hpMaxCannotBeReduced` (Acostumado à Morte-Vida), `conditionalRolls` (Resiliência Anã, Bravura, Sentido de Perigo, Sortudo — com `unlessConditions`, `deathSave`, `rerollNaturalOne`), `dropToOneHpInstead` (Resistência Implacável) e `slotRecovery` (lembrete da Recuperação Arcana). O alcance dos dois de crítico vem com o efeito (`ScopedSheetEffect`), e cada linha de ataque responde por `isSheetAttackInScope` (attackUtils), que pergunta à arma (`isWeaponInScope`) ou ao golpe desarmado (`isUnarmedStrikeInScope`). Bônus condicional da ficha (Aura de Proteção) entra nas notas da jogada com o mesmo texto da Revisão. Restrição de conjuração numa situação que o jogo não conhece é `castingRestriction` (a Fúria: em fúria não se conjura nem se concentra, p. 48; decisão de 2026-10-29, inclusive nas magias inatas da raça; e entrar em fúria encerra a concentração, decisão também de 2026-10-29: até o estado "em fúria" chegar com os efeitos ativos da Fase 2, gastar um uso da Fúria é entrar nela, e o recurso declara `spendEndsConcentration` com o motivo do aviso — o `spendResource` encerra a concentração no mesmo passo do desfazer, como a quebra automática): `getCastingRestrictions` (só para quem "for capaz de conjurar magias", `canCastSpells`: alguma fonte de `getSpellSources` ou característica que conjura sem ser fonte, o efeito `castsSpells` — Conselheiro e Andarilho Espiritual do Guerreiro Totêmico, Corpo Vazio, Artes Sombrias, disciplina elemental que conjura magia, Conjurador de Ritual) vai ao `RollGuide.castingRestrictions` — separado de `notes`, que é só o que está em vigor e pinta a caixa vermelha da aba Magia — e daí à linha da seção Conjuração, ao ataque de magia, à concentração (seção da aba Estado e `getConcentrationGuide`) e, na aba Regras, à seção Magias e à folha de toda magia. A Revisão e o PDF não ganham linha: o texto da Fúria já a diz.
- **Store com desfazer** (`stores/playStore.ts`): toda mudança passa por `run(op)`, que grava, empilha o estado anterior (até 30) e publica os avisos; o "Desfazer" do aviso só aparece quando a última ação mudou algo (`lastActionChanged`). Texto em edição (nota livre, nota de duração) registra-se em `registerPendingEdit` e é gravado no `close` e no `pagehide`.
- **Vitais fixos e PV** (`VitalsBar`, `HpPanel`; o que é só tela mora em `components/play/hpVitals.ts` e `hpEntry.ts`, nunca em `utils/playState.ts`). A barra é o PV atual sobre `getEffectiveMaxHp`, com cor por faixa (`getHpBand`); "PV baixo" é 0 < PV ≤ `LOW_HP_FRACTION` (1/4) do máximo — decisão de produto de 2026-10-28, não regra; a 0 PV quem fala são os testes contra a morte. Os temporários não enchem a barra. Os Dados de Vida e o "Descanso" ficam no bloco fixo; o toque leva à seção Descansos da aba Estado (`REST_SECTION_ID`), sem painel duplicado. O campo de dano e cura aceita "−7"/"+5": o sinal manda, sem sinal vale o botão (com PV temporários escolhido, o "+" continua temporário); é texto com `inputMode="numeric"`, e Dano/Cura levam o "−"/"+" porque o teclado numérico do iPhone não tem sinal — o número sem sinal e sem botão diz, em região viva, para escolher Dano, Cura ou PV temporários. Pela mesma razão (decisão de 2026-10-29), com ponteiro grosso (`(pointer: coarse)`: celular e tablet) nenhum texto do campo pede o sinal — placeholder "0", dica e aviso de texto inválido levam aos botões (`ENTRY_TEXT` no `HpPanel`); com ponteiro fino, ensinam o "−7 / +5". O atalho vale nos dois. O menos de todo campo de número do jogo (PV, rolador livre) passa por `normalizeMinus` (`hpEntry.ts`): "-", "−" e a meia-risca "–" do teclado do celular. O número de PV pisca no dano e na cura comparando um desenho com o seguinte (`getHpFlash`), o que pega toda mudança (painel, descanso, desfazer); o descanso longo e o desfazer dele (a leitura leva o `lastLongRestAt`) só piscam verde — os temporários e o ajuste do máximo que ele encerra não são dano. O pulso é `motion-safe:`, e com prefers-reduced-motion fica só a cor.
- **Rolagem na folha da receita** (`RollRecipeSheet`, Fase 1 fechada em 2026-10-28). Nas jogadas de d20, o Normal / Vantagem / Desvantagem é a circunstância da mesa que a ficha não conhece (o Mestre, Ataque Descuidado, Ajudar): entra por `withTableMode` (rollGuide) como a fonte "Circunstância da mesa" e se combina com as da ficha pela regra da pág. 175 — do mesmo lado não soma, uma de cada lado anula; a Inspiração gasta (`withInspirationSpent`) vem por cima, e a nota dela acompanha o modo. As duas passam pelo mesmo `addModeSource` (a fonte, o modo, a notação e a frase do que ela fez): fonte nova de modo na folha entra por ele, nunca com outra cópia da escada da pág. 175. A escolha é só da folha aberta: nunca vai ao estado de jogo nem ao desfazer, e o número da fórmula não muda. O resultado dos dados do app é sempre `RollOutcome` (receitas e rolador livre): dentro de um `aria-live` que existe antes da primeira rolagem, com `key` do registro; animação só `motion-safe:` (keyframes no `@theme` do index.css), o 20 e o 1 naturais só visuais (decisão 8). "Copiar resultado" usa `formatRollCopyText` (playDice) e não aparece sem `navigator.clipboard`. A cada rolagem a folha rola até o fim dela (a âncora do fim, com a margem do recuo de baixo), o que traz o resultado e, no ataque, o dano à vista no celular. O rolador livre (`FreeRoller`, aba Notas) só existe com `appDice` e grava por `logRoll`, como as outras rolagens do app.
- **Abas por swipe e densidade** (Fase 1, 2026-10-29). Deslizar o dedo de lado na barra e no conteúdo vai à aba vizinha (`useTabSwipe` em `components/play/tabSwipe.ts`, `adjacentPlayTab`, sem dar a volta), com o foco nela: só toque, só leitura dos eventos (a rolagem vertical é do navegador); não vale com dois dedos, começando em campo de texto, controle deslizante ou área com rolagem horizontal, nem com folha modal aberta dentro da área (`isSwipeExempt`). O arrasto de lado nunca é o "voltar página" do Chrome no celular, em ponto nenhum da tela: a raiz do `PlayScreen` declara `touch-action: pan-y pinch-zoom`, e, como quem rola (a faixa de chips, a lista do aviso, as folhas) recomeça o touch-action e o excesso do arrasto chegava à página, o `<html>` leva `overscroll-x-none` enquanto o jogo está aberto (no `body` ou nos contêineres não segura). Do md para cima a coluna alarga (`max-w-3xl` no md, `max-w-5xl` no lg: 48rem e 64rem sobre a raiz de 18 px, ou 864 px e 1152 px; os breakpoints seguem em 768 px e 1024 px, e a folha `sm:max-w-md` tem 504 px) e as abas viram grades, com as listas lidas de cima para baixo; abaixo do md nada muda — layout novo do modo de jogo entra só com `md:`/`lg:`.
- **Acessibilidade mínima** (Fase 1, 2026-10-29). Teclado no padrão da WAI-ARIA: a barra de abas tem tabindex móvel (só a aberta no Tab), setas que dão a volta, Home/End e ativação automática (`keyboardPlayTab`, em `playTabs.ts`); a exaustão é radiogroup com tabindex móvel e setas que marcam o nível vizinho (cada seta um passo do desfazer), **sem dar a volta** — do 0, a seta para a esquerda seria a exaustão 6, a morte —, e a tecla segurada (`e.repeat`) não sobe: cada nível pede um toque. Regra para controle novo ou mexido: o que some com a própria ação não larga o foco no body — ele vai ao controle que entra no lugar ou ao título da seção (`tabIndex={-1}`, com a ação em `flushSync` para o alvo já existir), nunca a um campo de texto, que abriria o teclado do celular a cada toque; recusada a ação, o foco fica. Botão que só se desabilita com o próprio toque é `aria-disabled`, não `disabled`, e apagado não faz nada: o "Aplicar" do PV, o "Gastar dN" do descanso curto, o "Registrar" do teste contra a morte, o "−"/"+" dos Dados de Vida do descanso longo e do rolador livre, o −1/+1/"Gastar" do recurso em poço e o "↶" do cabeçalho. O botão de envio apagado deixa o formulário enviar, então o formulário leva `noValidate` (o "Gastar dN", o "Registrar", o "Gastar" do poço): quem valida é o app, com o aviso dele, e a validação do navegador entraria antes do `onSubmit`, com o balão e o foco no campo numérico. Todos os controles do jogo que somem com a própria ação foram conferidos no navegador, pelo teclado (2026-10-29), e seguem a regra: concentração (iniciar → "Encerrar concentração", encerrar → título "Concentração"; o "encerrar" dos vitais → a inspiração, vizinha na faixa); aviso do pé (`NoticeToast`: o botão da linha passa o foco ao "↶ Desfazer" ou ao "OK" do aviso; o aviso fechado pelo próprio botão, à aba aberta, pelo `onFocusAway`); painel de PV ("Manter"/"Ficar com" → "Aplicar"; "+ Aumentar", "− Diminuir" e "encerrar" do ajuste → "± PV máximo"); descansos ("Gastar dN" no último dado do tipo e o "Desfazer o último dado" que esvazia o rascunho → a linha do dado; "Concluir", "Confirmar" e "Cancelar" → o botão do descanso); testes contra a morte (estável e morto → o título do painel novo; o 20 natural, "recuperei 1 PV" e "Fui revivido" tiram os testes da tela → o primeiro botão do painel de PV, `HP_PANEL_ID`, pela `onLeave`; "Rolar de novo (Sortudo)" → "Registrar"; antes de o foco sair do d20, a rolagem suave da queda a 0 PV, se ainda em curso, é interrompida — terminando depois do `focus()`, ela levava o alvo para trás dos vitais); condições ("Levantar" → o switch do Caído; o switch que fica só derivado, desligado com outra condição que a dá → o "regra" da linha); folha da receita ("Usar" e "Devolver" a inspiração passam o foco um ao outro; "Não foi crítico" → a fórmula; e, quando quem abriu a folha sumiu com a ação dela — o "Falhei: encerrar" leva o "Ver o que rolar" do aviso —, a `onFocusAway` do `PlayDialog`, que a tela manda ao "Desfazer"/"OK" do aviso que ficou, pelo ref do `NoticeToast` (`NoticeToastHandle`), ou à aba aberta); "Nova sessão" (perguntar → "Cancelar", cancelar → "Nova sessão", apagar → título do histórico). O título que recebe o foco mostra o anel do `*:focus-visible` do tema: nada de `outline-none` nele. Controle novo do jogo que some ou se apaga com a própria ação entra nesta lista, com o teste de componente. O foco também não fica atrás dos vitais fixos: com o jogo aberto, o `scroll-padding-top` do `<html>` é a altura deles mais o `STICKY_GAP` (ResizeObserver no `PlayScreen`), e o navegador o respeita ao rolar até o foco (o Tab para trás, o título que recebe o foco acima da vista). Região viva (`aria-live`) fica montada vazia antes do texto (o aviso do pé da tela, as dicas de valor inválido, o que impede o "Aplicar" do campo de PV): inserida já com o conteúdo, pode não ser anunciada — os testes conferem com `liveRegions()` (`__tests__/openPlay.ts`). Os avisos da abertura (correção da ficha, reconciliação) já estão na fila quando a tela monta: o `NoticeToast` os segura até o quadro seguinte. Resultado que só aparece no número, sem aviso (PV, usos e espaços, o rascunho do descanso curto), vai por `ChangeAnnouncer`, que anuncia quando o texto muda e nunca ao montar; num contêiner `space-y`, ele entra como primeiro filho (no fim, o irmão de antes ganharia margem). ## Persistência

- Toda leitura/escrita de ficha passa pela camada de storage **do próprio sistema**: `apps/web/src/systems/<sistema>/utils/storage.ts` (hoje `dnd5e` e `ordem`; no site, não no motor, que não conhece o navegador). O núcleo (`core/`) e a galeria global (`apps/web/src/GlobalGallery.tsx`) não acessam localStorage: usam as funções exportadas por essas camadas
- No `storage.ts` do dnd5e ficam a sessão do wizard (versionada por `SESSION_VERSION`) e a biblioteca; campo novo no draft ganha default em `withDraftDefaults` (e sanitização em `utils/draftValidation.ts`)
- O modo de jogo tem a sua camada, `utils/playStorage.ts`: o estado de jogo por ficha (versionado por `PLAY_STORAGE_VERSION`, campo novo com default em `sanitizePlayState`), as preferências (`appDice`, `keepScreenOn`; cada campo cai no seu padrão) e a ficha aberta no jogo (`saveOpenPlayId`, para recarregar a página voltar à mesa). Apagar a ficha apaga o estado de jogo dela (`deleteCharacter` → `deletePlayState`)
- **O arquivo exportado leva o estado de jogo** (decisão 10.2.3, 2026-10-29): envelope `CharacterFile` (`storage.ts`: `format: "dnd5e-character"`, `version: 2`) com o draft e o estado lado a lado, o estado com a versão dele; `parseCharacterFile` aceita também o draft solto dos arquivos antigos (versão 1, sem estado) e passa o estado pelo `sanitizePlayState` (estragado, não recusa a ficha). Importar sempre cria ficha nova, e o estado do arquivo vai só para ela, com o id dela (`importDraft(draft, playState)`): importar de novo uma personagem que já está no navegador nunca toca a ficha nem o estado de lá, então não há estados a misturar; os máximos se encaixam ao abrir o jogo (reconciliação)
- **Cópia de todas as fichas** (2026-10-29, `apps/web/src/libraryBackup.ts`, fora do núcleo porque conhece os dois sistemas): o "Exportar todas" da galeria baixa o formato `rpg-character-backup` (versão 1), com cada ficha no formato do exportar dela (a do D&D no envelope `CharacterFile`, com o estado de jogo; a do Ordem no draft), e o "Importar" da galeria reconhece a cópia e lê cada ficha pelo caminho do importar de uma. Restaurar cria fichas novas, como todo importar; a igual a uma daqui (a mesma ficha e o mesmo estado de jogo, sem a hora da gravação) fica de fora. Campo novo no envelope de uma ficha vale na cópia sem mexer nela
- **Salvamento automático do dnd5e** (decisão do usuário, 2026-10-26): toda alteração do draft é gravada sozinha, `AUTOSAVE_DELAY_MS` (400 ms) depois da última, e `pagehide`/`visibilitychange` (hidden) gravam na hora (`stores/characterStore.ts`). Setter novo de draft passa por `editDraft` — `set` direto não agenda a gravação. Ação que troca de ficha (abrir, nova, importar, duplicar, galeria, Concluir, jogar) chama `flushAutosave` antes; excluir a ficha aberta cancela o timer, navegar entre etapas também (já grava tudo). O modo de jogo nunca chama setter de draft (o estado de jogo vai pelo `playStore`/`playStorage`), então `exitPlay` e o `pagehide` no jogo não têm o que gravar (teste em `characterStore.test.ts`). Regra de existência (`shouldPersist`, uma só para navegação, salvamento automático, galeria e Concluir; 2026-10-28): ficha que já está na biblioteca é sempre atualizada — apagar o nome não descarta as escolhas; a nova só entra com nome ou com alguma escolha fora da etapa Nome (`hasDraftContent`; o nível sozinho não conta) — percorrer o wizard em branco não deixa "(sem nome)" na galeria
- A V1 implementa essas camadas usando localStorage
- Componentes e stores **nunca** acessam localStorage diretamente
- Isso permite migrar para IndexedDB no futuro sem refatorar a aplicação

### pt-BR × inglês (decisão de 2026-10-25)

O livro do projeto é o PHB 2014 em português (`docs/_book-extracts/dnd-phb.txt`). Quando o pt-BR diverge do original em inglês por **erro claro de tradução que muda a regra**, os dados seguem o inglês; diferença só de redação, sem efeito de regra, fica com o pt-BR. Cada caso adotado entra na lista abaixo e num teste em `data/__tests__/bookText.test.ts` (o extract carrega o erro: copiar o trecho de novo, ou rodar `scripts/parse-spells.mjs` sobre `docs/magias`, o traria de volta — por isso a digitalização em `docs/` acompanha a correção quando os dados saem dela).

Casos que seguem o inglês:

- **Colheita Sinistra** (mago necromante, p. 100): o triplo é do nível **da magia**, não "do seu nível".
- **Pedra de Transmutador** (mago transmutador, p. 101): trocar o benefício vem com magia de **transmutação**, não "de conjuração".
- **Conjuração de Ritual do clérigo e do druida** (p. 65 e 73): magias **preparadas** com o descritor ritual, não "que você conheça" (texto copiado do bardo).
- **Ilusão Menor**: componentes **S, M**, não "V, M" — a magia não tem componente verbal.
- **Presença Intimidante** (bárbaro Furioso, p. 49): a ação seguinte estende o medo até o **fim** do próximo turno, não o "início".
- **Golpe de Sorte** (ladino 20, p. 92): vale para **teste de habilidade** (não "um teste qualquer", que abriria para resistência), e o d20 vira 20 (sem "natural").
- **Correntes de Cárceri** (invocação do bruxo, p. 61): pré-requisito **Pacto da Corrente** (`requiresPick: pact-of-the-chain`), não "característica Corrente de Cárceri", que não existe.
- **Golpe desarmado** (p. 197; decisão de 2026-10-29): é **ataque corpo a corpo com arma** ("melee weapon attack"), sem ser arma — o pt-BR o opõe ao "ataque corpo-a-corpo armado". Valem nele o Dano de Fúria, a margem do Campeão ("seus ataques com armas") e, só quando ele tem dado (Artes Marciais, Especialista em Briga), o Crítico Brutal e os Ataques Selvagens, com o dado do golpe (decisões 20 e 21 de `regras-dano-e-morte.md`, revistas em 2026-10-29); Duelismo, Armas Grandes e Arquearia, não. A frase da regra não está nos dados: o teste prende o comportamento (a nota na linha do golpe desarmado).
- **Ataques Selvagens** (meio-orc, p. 41; decisão de 2026-10-29): "When you score a critical hit with a melee weapon **attack**" — o texto diz "com um ataque corpo-a-corpo com arma", não o "com uma arma corpo-a-corpo" do pt-BR, que deixaria de fora o golpe desarmado com dado, onde o traço vale (regra acima). O Crítico Brutal (p. 49) já dizia "acerto crítico corpo-a-corpo", como o "melee attack" do inglês.
- **Destruição Divina Aprimorada** (paladino 11, p. 111; decisão de 2026-10-29): "Whenever you hit a creature with a melee weapon" — exige **arma** corpo a corpo, e o golpe desarmado fica de fora. O pt-BR diz "com um ataque corpo-a-corpo", e o "ataques corpo-a-corpo com arma" da frase anterior o alcançaria pela regra acima.

Avaliado e mantido no pt-BR: **Presença Dracônica** (feiticeiro dracônico 18) — nenhuma das duas edições dá a CD da resistência, então não há divergência a corrigir.

**Ortografia e concordância** erradas no livro ou na digitalização (acento faltando, "criaturas tem", "um criatura") são corrigidas nos dados quando não mudam sentido nem regra (decisão de 2026-10-26); em dúvida, fica. A grafia anterior ao Acordo Ortográfico que o livro usa ("corpo-a-corpo", "não-mágica", "bem sucedido") ficou fora dessa correção. Como os casos de tradução, a forma errada fica presa em `bookText.test.ts`, e a digitalização em `docs/magias` acompanha a correção das magias.

- Cobertura **recomendada** para utilitários puros em geral
- Componentes de UI: testar comportamento crítico (ex: fluxo de seleção), não cobertura exaustiva

## Workflow do Claude Code

1. **Sempre propor um plano antes de implementar** — aguardar aprovação do usuário
2. **Nunca chutar regras de D&D** — perguntar ao usuário se houver dúvida sobre uma regra; consultar `/docs` quando o trecho relevante já tiver sido digitalizado
3. **Commitar a cada feature concluída** — commits atômicos com mensagem em português
4. **Atualizar este CLAUDE.md** quando novas decisões arquiteturais surgirem, em commit dedicado com prefixo `docs:`

## Definição de Pronto (Definition of Done)

Uma feature está pronta quando:

- Implementação concluída
- Tipos TypeScript corretos e estritos
- Testes escritos (quando aplicável conforme seção "Testes")
- Funciona localmente sem erros no console
- Commit feito com mensagem clara em português
